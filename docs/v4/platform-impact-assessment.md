## Platform gates before future V4 implementation

1. **Actual source context before replay and inside the transaction.** `CommandPipeline.cs:44–68` authorizes its supplied spec, then can return a saved result before the command body resolves source context. The idempotency store key is globally unique (`Migrations/0001_kernel_foundation.sql:90–96`; `PostgresStores.cs:330–357`) and its fingerprint covers command type/body, not actor or resolved authorization context. New V4 commands must resolve actual source attributes and current authority before result replay, then re-resolve/lock sources and validate source/policy versions before mutation. Keys should be scoped or bound to originating identity/command/source; random key uniqueness alone does not establish actor safety. A revoked program, expired delegation or changed classification must not become readable through a prior command result. This is an architecture gate, not a V3 change in this session.

2. **Do not treat generic audit access as classification-safe evidence export.** Successful audit writing at `CommandPipeline.cs:81–97` does not populate `AuditEntry.Markings`; `KernelReadStore.cs:55–72,77–96` selects program membership without markings or full source context. Preserve existing audit records; add scoped/redacted projections and exact source resolution for new QMS export/retrieval, and design a separately approved additive audit classification extension. Unknown historical ownership/classification must fail closed or be explicitly resolved by authorized policy, rather than inferred to be public.

3. **Current access at notification delivery.** Inbox reads recheck role/program/markings, but recipient selection at `NotificationEventSubscriber.cs:147–156` checks only active identity, role expiry and program. It does not accept/check event markings. Email worker SQL at `NotificationDelivery.cs:43–59` and send at `:87–97` use the queued recipient/message with no fresh role/program/marking/permission/source check. Sensitive QMS notifications therefore need recipient/source resolution at the final delivery boundary, suppression/redaction for revoked access, and tests for queued-delay revocation, deactivation, delegation expiry, resolution notices and classification. A deep link must reauthorize every source. External customer/supplier contact remains a separately authorized human action, never a consequence of a traceability suggestion.

4. **Retention is missing and physical purge conflicts with immutable history.** No structured retention policy, retention trigger/duration, legal-retention hold, disposition authority, destruction-evidence model or purge API was found in source. Immutable file/revision/evidence/link guards prohibit deletion (`0005_documents.sql:16–23,110–116`; `0012_business_evidence.sql:6–12,44–45`). Initial V4 should add policy/hold/disposition-eligibility metadata while preserving every source and file. Do not quietly weaken these guards to implement a Destroy button. Actual destruction needs a distinct later design decision covering deduplicated shared hashes, live foreign keys, audit/signatures/genealogy, backups/replicas/exports, legal holds, evidence manifests and retained tombstones. No universal retention period is inferred from ISO.

5. **Signature wording and correction semantics.** Human source-signature verification and Forge electronic signoff are distinct. Neither currently establishes PKI signing, trusted timestamp, cryptographic external-signer validation, legal equivalence or compliance with another regulatory signature regime. Proposed QMS signatures should bind the exact source version and policy fingerprint, trusted identity/assurance and explicit meaning at commit. Corrections append superseding/withdrawal attestations with reason and links; they must not rewrite frozen source files or historical decisions. Existing unique evidence verification per revision does not supply this future correction lifecycle automatically.

6. **Runtime evidence and multi-host delivery.** Subscription checkpoints at `EventSubscriptions.cs:43–83` have no subscriber lease/transaction with the external side effect; duplicate processing and checkpoint races require explicit tests and a supported-host topology. Relay ordering with several hosts should not be assumed to provide causal total order merely from SKIP LOCKED. QMS projections should follow source version/causation and tolerate retries/out-of-order arrival. Poison events require durable quarantine/replay decisions and lag monitoring without reversing successful business commands.

## Failure, concurrency, scale and validation proposal

Future implementation acceptance should cover the following before release; none of these tests were executed in this architecture-only review.

- Boundary tests: new QMS code only accesses other context contracts; no second Inventory/Genealogy or direct database calls in engines; source ownership remains explicit. If a new context is chosen, register it in the architecture inventory and migration ordering.
- Access matrix: actual A versus B program/facility/work center/contract/customer/shift, mixed-source evidence selections, markings, inactive identities, insufficient assurance, expired qualifications/delegation, grantor revocation, scope change and independent approval. Repeat through API, inbox, attachments, Analyst, reports/export, download and delayed notifications.
- Replay tests: same key/same actor/body yields one accepted decision/audit/event; same key/different body conflicts; changed actor, revoked source/program/marking or policy version cannot disclose or apply stale result. Require fresh actual source authorization before replay.
- Race tests: simultaneous approve/release/correct, hold placement versus release/shipment, calibration/qualification expiry versus action, retained binding versus disposition eligibility, legal hold placement versus disposition decision, signature policy change versus commit, label replacement versus accepted scan, export generation/download versus access revocation. Lock/version comparison yields exactly one valid result and preserves originals.
- Evidence tests: exact historical revision, file-hash consistency, source signature review distinct from signoff and acceptance, stale version rejection, correction creates superseding evidence and leaves originals readable, hash-chain break detection, privileged-access assumptions documented, unknown historical scope fails closed.
- Retention tests: unknown/late trigger, changed effective policy, longest applicable policy, overlapping legal holds, hold release does not itself destroy, shared deduplicated hash attached to retained and eligible records, backup/export/replica implications, immutable records survive upgrade. Prove initial metadata operations cannot delete any source/file.
- Delivery tests: crash before/after outbox commit, duplicate event, out-of-order causation, external success before checkpoint failure, several hosts, provider idempotency, poison event, quiet hours/DST, expiry worker replay, queued-recipient revocation/classification, no network outage rollback of accepted source transaction. Measure subscriber lag and recovery.
- UX/terminal tests: A-to-B switch with pending scan/command, stale responses/dialog, idle and dispose, device outage, ambiguous accepted result and safe reconciliation, scan conflict explanations, keyboard-only/scanner wedge/focus/live-region behavior. Physical hardware and real Nexus remain deployment validation.
- Scale tests: indexes on source/type/ID/version, retention next-action/hold state, QMS due/state/owner/scope and source evidence links; cursor pagination; bounded traversal and pack size; avoid new list-all-and-filter target lookups. Current resolver examples at `DocumentTargetResolver.cs:131,159,168` use broad source lists, unsuitable as a pattern for scaled QMS links. Current 50 MiB files materialize byte arrays; a future large-pack design must stream without duplicating authoritative blobs. The global audit-tip lock and full-chain materialization (`PostgresStores.cs:290–319`; `KernelReadStore.cs:101–116`) need measured contention/memory budgets before high scan volume.
- Migration/regression tests: populated baseline upgrade, idempotent migrations, checksums unchanged, all historic hashes/versions/signatures/links/genealogy/balances unchanged, restrictive unknown context, rollback and restore. Run prior relevant V3 regression suite only when future implementation is authorized. Validate real Nexus/Sentinel/email contracts, production restore and access-sensitive export in deployment separately from local fake receivers.
