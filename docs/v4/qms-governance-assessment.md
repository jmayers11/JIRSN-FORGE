## Three reuse limitations that materially affect V4

1. **The existing inspection KPI is mislabeled for QMS FPY use.** Catalog text calls it “First-pass acceptance” at `src/Forge.Planning/Reporting/StandardReports.cs:130-137`. Implementation reads all inspections in the interval, converts passing inspection quantity to accepted quantity, then divides total accepted by total inspected at `:1756-1781`. It has no first-attempt/cohort selection. `InspectionInfo` at `src/Forge.Quality/Contracts/QualityContracts.cs:42-54` has no physical inspected cohort/attempt identity. Therefore reuse it as an inspection acceptance fraction with its limits; genuine first-pass yield needs stable first-attempt lineage/cohort, reinspection treatment, partial quantities, no double-counting and unit/scope rules. Do not revise historical V3 values in this session.

2. **Presentation row limits are unsuitable for complete QMS aggregate reuse.** `src/Forge.Planning/Reporting/ReportService.cs:103` sets 5,000 rows. `:164-181` truncates before Groups and Total aggregation while builder summaries may derive from the entire body. High-volume dashboard/management-review figures must aggregate the complete authorized population before pagination, explicitly disclose any incomplete source/coverage, and preserve metric version/source cutoff. A bounded report is still useful for drill-down; its displayed total is not automatically the QMS population total.

3. **CAPA context needs strengthening before adding new sensitive origins.** Creation uses `ResourceRef.Of("Capa")` at `src/Forge.Quality/QualityService.cs:413`, checks only that the linked NCR exists at `:416-418`, and transitions use ID-only `ResourceRef` at `:491-501`. API list at `src/Forge.Host/Api/QualityEndpoints.cs:52-53` is a broad QualityRead list. CAPA contract has no owner/program/marking scope. Preserve current engine but extend source-derived scope, field sensitivity and transactional source authorization, current read filtering, multi-source visibility intersection and revocation behavior. An audit/complaint link must not widen access to a private production or customer source.

## Audit/evidence and revision-transition model

`EvidenceRef` is a typed source reference, not a duplicated business fact: source context/entity/key, immutable source version or event/record ID, event/effective time, creation metadata, file revision/hash when present, provenance, retention class and sensitivity. Assessment links can cite both structured transactions and exact source file revisions. Extending attachment `DocumentTargetType` should use existing Host resolvers and Engineering's evidence store; Quality owns the adequacy decision. Missing source, unknown historical context, no permission and insufficient evidence are different states, without disclosing hidden records.

For an audit evidence package: preserve audit criteria/version/scope/sample selection/cutoff, applicable procedure version, authoritative transaction IDs, relevant operation/qualification/inspection/release decisions, author's statement and auditor's signed assessment. Retain case-specific interpretation and contrary evidence; a search returning attachments is not “clause compliant.” Current record access is rechecked when viewing historical packages; approval to the package must not grant wider access to underlying sensitive records.

Standard mappings use a standards registry `(publisher, identifier, edition, amendment, source-reference verification status)`. Store references to licensed source and organization interpretations subject to permitted distribution; don't embed unauthorized full normative text. Map 2015(+relevant amendment) to 2026 as many-to-many references with relationship (retained/changed/moved/new/removed/uncertain), reviewer, licensed source provenance, rationale and procedure/evidence implications. Without source verification, each detail remains Unverified. A standard edition update marks affected maps/assessments ReviewRequired while preserving earlier signed assessment and exact evidence history. Do not migrate existing organizational evidence to new “compliant” status automatically.

## UI and Analyst changes

One Quality workspace can expose proportionate views: operational Quality, QMS governance/objectives/risks, supplier/customer quality, audits/CAPA, and management review/evidence. Records show source links, applicable revision, owner/due dates/state, next permitted action, reason for blocked action and evidence gaps. Small shops can use short forms and qualitative assessments; configured high-volume factories can use bulk derived metrics and scoped exceptions. No universal checklist or forced scan, FMEA, climate score, ethical-behavior questionnaire or mandatory approval bureaucracy is added by this proposal; requirements classification and applicability determine what is enabled.

Extend existing Analyst deterministically with “overdue corrective actions,” “audits with open findings,” “objectives below target,” “evidence linked to requirement reference,” and “changes since last management review” only after their source records and authorization exist. Genealogy, holds, qualification-expiry and tool-history questions reuse existing report routes where supported (`QueryParser.cs:472-477`, `:551-557`; ADR0050:11-21). For “what evidence supports clause X,” resolve standard/edition/scope, distinguish evidence found from adequate assessment, and show reference not verified when applicable. Unsupported/ambiguous clauses require clarification. Management-review comparison requires the saved review input cutoff, not an arbitrary “what changed” current schedule comparison.

Add dashboard/export context: metric definition/version, calculation vs human assessment, cohort/scope/window/time zone, source cutoff, numerator/denominator/unit, completeness/warnings and source drill-down. Central QMS review visibility does not authorize export of private customer/program facts. Optional narration remains permission-filtered/downstream and labels uncertainty; no independent conformity or root-cause conclusion.

## Dependency order and proportionality

The request's V4.1→V4.6 sequence is broadly usable, but QMS/evidence/contracts must begin before all scans are shipped. Recommended dependency gates:

1. **Architecture/standards/product gate:** approve licensed verification process, domain ownership, retention/source identities, assessment meanings and current V3 reuse limitations. No code until Product Owner approves review.
2. **Shared foundations (early part of V4.1):** source-qualified identity/reference/version/evidence/access contracts; source-context CAPA extension plan; full-population metric contract; governed applicability/required assurance. Scanning is an optional adapter over authoritative commands, not a QMS prerequisite.
3. **Operational execution/investigation (V4.2):** inspected-cohort/measurement-use/product-release links and historical trace investigations. Existing Inventory/Genealogy/Quality/Resources remain authoritative.
4. **Thin governance (can start with steps 2–3; V4.3):** controlled QMS scope/process owner/applicability/policy; risk/opportunity/objective definitions and action tracking. These decide which operational inspection/design/scanning controls apply. Metrics with incomplete data are explicitly unavailable, not estimated into conformity.
5. **Supplier/customer quality (V4.4):** supplier evaluation scope and customer identity/accepted-requirement review; complaint/feedback/RMA/CAPA links. Dependencies are operational sources/evidence/authority and thin governance, not all barcodes.
6. **Audits/existing CAPA extension (V4.5):** auditor criteria/competence/impartiality, human finding assessment, source links, supported causes and effectiveness; no new corrective-action engine. Internal audit can precede full customer dashboards if missing inputs are recorded.
7. **Management review/edition mapping/dashboard (V4.6):** aggregate all available governed source inputs using complete metric populations and frozen cutoff. Begin verified standards registry and edition mappings in step 1, then wire actual evidence/assessments here. Don't postpone licensing/edition verification until the last increment.

One engine serves all four request archetypes: small machine shop (qualitative risks, short audit plans, optional scans); capacitor plant (bulk lot/cohort metrics/partial inspection and full aggregates); build-to-print aerospace supplier (customer-restricted revision/requirement evidence and justified design nonapplicability); outsourced special-process manufacturer (Procurement provider approval scope plus existing processor dispatch/return/custody/certificate trace). Vary policy/applicability/evidence/permitted-action configuration, not QMS databases or genealogy systems. Sector/customer requirements are independently classified; this proposal does not claim ISO 9001 alone satisfies sector standards.
