## Identification and label proposal

1. Use a versioned canonical reference envelope with organization namespace, entity type and the authoritative key. Examples: person GUID, production-order number, operation `(order, sequence)`, instance `(part, lot)`, resource/tool code, warehouse location code, container code, inspection ID and shipment ID. Use a length-bounded canonical encoding/escaping; no concatenation whose delimiters can collide. Resolve through context-owned `.Contracts`, returning permitted display data, type and current context. Unknown/ambiguous/cross-organization references fail clearly. Legacy/manual and customer/supplier barcode aliases require controlled mappings to the same canonical reference, not new entities.
2. A label is a presentation record: LabelId, canonical entity reference, label template/version, human-readable identifier and configuration, symbology, issued timestamp/actor, device/printer if known, print job state and correlation. Track print request, confirmed/failed/uncertain print, reprint reason, replacement/void and superseded label. Printing must never insert stock. A print request/spool acknowledgment is not proof the label physically printed or was attached.
3. Where individual label-copy tracking matters, put LabelId alongside canonical reference in the payload. Reprint/replacement creates a new label record linked to the same entity, preserving all inventory history. A void label never voids the material. Policies decide whether multiple valid labels are legitimate (a batch spanning containers) or forbidden (a single serialized unit's sole identification).
4. E's duplicated physical sticker cannot always be detected from equal barcode text. A repeated scan is often legitimate. Detection comes from a tracked label copy, serial/location uniqueness, impossible simultaneous state and operator conflict confirmation. Do not promise detection of two indistinguishable stickers before a recorded conflict. `tests/Forge.Integration.Tests/InventorySerialIntegrityTests.cs:11` already distinguishes an impossible serial in two places from a valid lot split/move.
5. Input adapters support keyboard-wedge, camera and future industrial readers; symbology is presentation/transport. Scanner input is untrusted, cannot execute arbitrary URLs/commands, and is parsed within length/type limits. Manual search is an authorized alternative with provenance where policy permits it. Device branding belongs in adapters, not business rules.

## Scan-to-execute proposal

Keep one configurable execution workflow over existing commands:

`identify operator / assure session -> resolve order -> resolve operation -> show applicable controlled instruction -> resolve actual material and required equipment -> authoritative readiness check -> start -> report actual quantity -> identify outputs -> required inspection -> authorized release -> completion/signoff`

Each operation policy selects necessary scans, checks and assurance according to actual process requirements. Existing settings for document enforcement, training, tooling and generalized hold activities remain useful. A stable machine/location terminal can supply trusted context without making an operator rescan the same object unnecessarily. Never turn all 18 entity types into mandatory scan steps.

The session records current operator and authenticated actor, operation, policy version, intended material/configuration, displayed instruction revision/hash and selected resources. A person switch, lock, expiry or outage invalidates staged work and earlier responses using the existing terminal-session revision pattern. Consequential steps recheck assurance, actor, qualification, required document effectivity, material status/revision/quantity/location, actual tool validity, predecessor and inspection status on the server. The displayed instruction must match the applicable approved revision, which can legitimately be older than the newest revision. A missing source/coverage is explained, not guessed.

A readiness preview is explanatory, never a standing permission. Apply the shared pure checks again inside the existing command pipeline/unit of work before any write. Use existing stock/operation concurrency locks, idempotency keys and expected record versions. A material scan proposes a selection; `Issue`/`Consume`/`Transfer`/`ReportProduction` commands alone create the recorded facts. Steps commit individually and expose resumable state; the entire factory workflow is not one database transaction.

ScanAttempt should capture resolved reference/type, stage, server timestamp, device/session, operator/authenticated actor, required assurance summary, validation code/reason, correlation and accepted business transaction ID. Keep raw attempt telemetry separate from authoritative accepted transactions; use bounded retention/redaction and avoid persisting badge secret, PIN or tokens. Accepted commands continue through existing audit/outbox infrastructure. Rejected scans must be understandable and not silently override requirements. Outages follow the existing lock/no-offline-queue behavior (`terminal-state.mjs:1`); durable offline production is a separate explicitly designed capability.

## Investigation and release domain additions

Add to existing Quality/Resources owners, with typed references to the existing entities:

- TraceabilityInvestigation: trigger/source, human owner, scope, status/version, data cutoff, query version, candidate evidence paths and completeness/gap flags; append CandidateAssessment with include/exclude/uncertain rationale, evidence and approver; link separately authorized kernel Hold commands and customer/return/CAPA records.
- MeasurementResourceFinding: exact gauge/tool, as-found issue/affected characteristic range, discovery/recorded timestamps, suspected use interval, determining evidence and reviewer. Join recorded gauge-use/inspection times to exact subjects, then traverse existing genealogy/shipments. Distinguish original recorded valid-at-time status from a later risk assessment. Interval selection and disposition belong to Quality.
- ProductReleaseDecision: exact material/order/output and quantity/serial scope, frozen requirement/acceptance summary, inspection coverage rule, applicable concession, authority/assurance/signature and version, release timestamp and revocation/correction history. Apply approved decision through the existing ledger. Keep acceptance and release separate where configured requirements require it.
- Inspection extensions: frozen criteria/plan version and units, exact inspected subject and coverage/sample policy, per-result equipment/time and evidence links. Existing receiving/FAI/production inspection records remain authoritative and gain common reference contracts.
- PropertyAgreement/PropertyIncident: legal owner, custody event links, authorization scope/term, condition, permitted process/use and customer return/acceptance evidence. Reuse Resources tool identity and Inventory instance identity.

Add label/scan presentation tables once in shared infrastructure (or a narrowly owned identification adapter context), with no independent stock quantities, genealogy or authentication. Entity resolvers must obey context boundaries and contextual authorization. Add indexes for tool/inspection/use interval, inspected subject, label-copy reference/state, release scope and investigation evidence retrieval. Preserve old records as unknown where new fields were not recorded; do not backfill inferred lot/equipment/owner or declare complete traceability. Existing append-only history protections are valuable under their database privileges, not a guarantee against privileged database administrator changes.

Proposed APIs are bounded resolve/label/scan-session endpoints that call existing commands; Quality endpoints add investigations, historical calibration impact, inspection coverage and release decisions. Scanner UX presents the current operator, applicable work/configuration, the next necessary step and actionable block reason. Quality UX groups physical stock, WIP, reserved allocations, shipments and unknown links with evidence and authorized decisions. No scan UX should expose internal schema names or force operators to interpret compliance clauses.

## Four configurable archetypes, one core

| Archetype | Configuration using shared engine | Tradeoff and needed proof |
|---|---|---|
| Small machine shop | Few work-center/order/lot scans; manual authorized identification fallback; simple inspection plan and release authority; document/qualification/gauge gates as required. | Avoid mandatory device fleet, serialized traceability or universal scoring methods. Minimum useful evidence still needs exact configuration and accountable release. |
| High-volume capacitor plant | Batch/roll/reel identity, quantity-conserving transformation, material genealogy, approved sampling/coverage and optional reader ingestion; configured automatic context/quantity acquisition. | Per-unit scanning is often excessive; batch granularity limits isolation precision. Current whole-site graph construction/500 inspection caps need complete indexed/paged reads and measured throughput. Automatic inspection ingestion requires schema/unit/integrity validation. |
| Build-to-print aerospace supplier | Customer/program access, controlled customer drawings and configuration, lot/serial provenance, FAI where required, customer concession/acceptance and special equipment/qualification assurance. | Stricter policy and evidence burden; explicit customer/sector requirements are separate mappings. ISO alignment alone does not establish aerospace conformity. Preserve legitimate order-specific old-revision applicability. |
| Outsourced special processes | Approved service PO/technical package, recorded sent specification/configuration, same physical instance with supplier custody, return inspection/certificate/release, provider approval scope and preservation requirements. | Avoid fictitious new inventory on dispatch/return. Some transformations genuinely create child identity and must record that relation. Certificate completeness does not replace configured process qualification/validation or human acceptance. |

The four archetypes vary requirements, granularity, inspection coverage, authority, devices and retention; they share Inventory/Execution/Resources/Engineering/Quality/Kernel records. Avoid four policy engines. Required early Product Owner decisions: exact traceability granularity; label-copy/replacement policy; identification/assurance at shared terminals; scan-policy defaults; inspection sample/quantity coverage; independent product-release authority; retrospective calibration interval rules; customer-property legal ownership; retention of rejected attempts and real-volume performance targets.

Suggested dependency correction: resolve the shared command validation and inspection subject/release semantics before promising a complete scan workflow. Identity/labels can precede Quality execution, but general scan-to-execute cannot be marked complete while safety/readiness are only read-side projections. Foundational governed requirement/configuration and release policies belong before the implementation of their gates; audit/evidence views can then consume the facts.
