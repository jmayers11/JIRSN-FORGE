# ADR 0040 — V3.16 identity, step-up, workstations and signatures

Status: accepted after full verification.

Forge keeps authentication, authorization and job qualification distinct. OIDC supplies the signed-in identity; Forge's permission policies determine whether that identity may issue a command; the existing operator-authorization engine still determines whether a worker is qualified for the operation. Selected approval endpoints add a step-up check requiring an accepted provider `acr` value and a fresh `auth_time`. Defaults are `urn:forge:assurance:high` and 300 seconds; deployments configure `Forge:Authentication:StepUp:AcceptedAcrValues` and `MaxAgeSeconds` to match their identity provider. The maximum accepted age is clamped to one hour. Missing, weak or stale assurance returns an OAuth insufficient-user-authentication challenge before the approval handler runs.

Identity lifecycle uses a SCIM PatchOp endpoint, enabled only with `Forge:Authentication:Scim:Enabled`. A provisioner must have the configured scope (`Forge:Authentication:Scim:ProvisioningScope`, default `forge.provisioning`) and can deactivate a Forge person by IdP subject. The operation uses the normal command pipeline, writes an audit record and durable event, and marks the person inactive. API access is denied and badge identification filters out badges belonging to inactive people. Production must configure and validate the Nexus issuer, audience, signing keys and provisioning scope through the host's JWT bearer configuration. Development-header tests verify Forge's endpoint contract; they do not verify a live Nexus issuer or network connection.

Shared shop-floor terminals keep badge credentials in page memory. The active operator is shown after identification. After 60 seconds without activity, or when Lock terminal is selected, the page clears the operator and badge and returns to the scan screen. Switch user clears the current identity before another badge is accepted. Server commands still authenticate the terminal principal and verify the badge/PIN for the acting worker; terminal login alone does not establish worker qualification.

Execution signoffs persist signer role, assurance method (`Badge+PIN`) and the execution record version alongside the existing signer and signature data. Evaluation uses a version compare-and-set and increments the record version, so the signoff is bound to the evaluated record revision. A workforce migration adds durable failed PIN counters; five consecutive failures lock the badge for ten minutes. PIN verification uses a transaction separate from the business command so a rejected PIN's counter and outbox event survive command rollback. A successful verification resets the failure state.

Forge's durable outbox can send authorization-denial, badge-PIN-failure and identity-deactivation events to a configured Sentinel endpoint. Delivery is idempotent by event ID and requires HTTPS outside Development. Configure `Forge:Sentinel:SecurityEventsEndpoint` and its bearer token in deployment secret storage. Sentinel has no compatible intake endpoint in the local project at this checkpoint, so automated coverage uses a fake receiver and deployment still requires a real receiver. No live Nexus or Sentinel integration was exercised.
