# ADR 0039 — V3.15 configurable authority

Status: accepted after full verification.

Roles and permission grants move into the Kernel database. Migration 0003 seeds role definitions and permission grants from the existing role map, excluding system-only roles. The integration parity test compares each seeded permission set with the previous map so the migration does not silently widen or narrow access. Runtime principals load effective grants from the database; system actors and in-memory kernel tests keep the existing static fallback.

A role permission can be unscoped or scoped to a program, facility, work center, contract, customer or shift. Once scopes exist for a role/permission pair, they replace that role's global grant. Resource references carry these contextual dimensions into the single authorizer. Approval threshold policy associates a maximum amount and three-letter currency with a permission; a protected action must supply known matching amount/currency, otherwise the configured limit fails closed.

Role assignments may expire within one year. Principal resolution and directory listings filter expired assignments at read time. Reassigning a role after an expired assignment renews its row. The initial separation policies make self-role changes and self-program changes configurable through audited commands; disabling self-role protection remains prohibited to prevent administrative lockout. SecurityAdministrator's permission policy is immutable through the new APIs.

Role creation, policy changes, separation policy changes and threshold changes use the normal command pipeline for authorization, reason, idempotency, event and audit. All current permission values form a fixed catalog; custom roles can combine those actions without adding new code permissions.

Verification: quick Release build passed with zero warnings/errors; Planning 266/266 and Architecture 32/32. Full `verify.cmd` passed with Planning 266, Architecture 32, Kernel 33 and Integration 100 tests; the Release build had zero warnings/errors. The V3.15 PostgreSQL acceptance checks passed within the full suite, including exact seeded permission parity, data-backed authorization changes, scope and amount/currency threshold enforcement, expiry, configurable separation of duties and migration idempotency. Evidence: `.forge-logs/quick-v315.log`/`.status` and `.forge-logs/verify-v315.log`/`.status`.

Current boundary: project decisions supply the recorded USD budget, and source selection supplies the actual quote total/currency. Unpriced POs and RFQ releases do not invent amounts; a configured monetary threshold denies them when the required value is unknown. With no configured threshold, existing authority rules still apply. The completion-audit tests verify this behavior and both grantor/recipient ceilings on delegated actions.

## Governance scenario F completion

Expiring role assignments remain supported, but they are not the delegation model. Migration 0006 adds temporary permission delegations with a recorded grantor, recipient, permission subset, intersecting scope dimensions, start and expiry, proposal reason, independent approver and approval reason, and revocation history. A separate `kernel.delegations.propose` business action is seeded on existing roles; custom roles can receive it by policy. The grantor proposes only authority from their own current roles; neither borrowed authority nor access/delegation administration can be lent. The approver requires access-management authority and cannot be the grantor or recipient. Actual action amount thresholds continue to govern borrowed actions; requesting a delegation is its own action rather than a fictitious monetary transaction.

Effective principals receive separate delegated permissions only after approval and during the half-open interval `[start, expiry)`. The authorizer also checks this interval so a principal retained past expiry cannot act. Each resolution checks that the grantor remains active, keeps the required role authority and retains any requested program membership. Recipient program membership and markings remain independent authorization gates; delegation does not modify base roles or grant program access. Each delegated grant retains the source action amount/currency threshold and must satisfy both source and recipient policies. Role expiry, delegation expiry and principal directory resolution use the same host clock. A new interval can be proposed without rewriting previous records.

Facility/capital project approval, subsequent change decisions and cancellation now supply the recorded USD budget to the shared authorizer. The command locks the project and refuses if the authorized budget changed before commit; all project mutations use that row lock. The real API acceptance checks that a borrowed $1,000 approval succeeds at the boundary, a $1,001 draft or budget increase is denied, and tightening the source policy to $900 affects the next action immediately. Cancellation at $900 succeeds under the tightened policy while cancelling the $950 draft is denied.

Commands use the existing Kernel transaction, audit chain, event outbox and idempotency path. The Settings screen supports proposing, independently approving, inspecting and revoking temporary delegation. `TemporaryDelegationTests` exercises real API order creation before start, during the approved scope and at expiry; scope widening, source revocation, program membership, re-delegation and approval separation are denied, and base roles remain unchanged. Focused and full verification results are recorded in the release handoff.
