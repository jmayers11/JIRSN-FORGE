# Daily Mission & Role-Based Workspaces — Phase 0 Review

Reviewed 2026-10-25 against `Forge_Daily_Mission_Role_Based_Workspaces_Implementation.md` and the current Forge source.

## Finding

This is a new product feature, not a visual polish pass over an existing Daily Mission page. There is no Daily Mission or Daily Plan route, mission projection, first-login briefing, per-operational-day dismissal record, or mission decision workflow in the current client or host. The attachment is an implementation specification with an illustrative schema; its embedded “implementation request” is treated as project requirements, separate from the owner’s request to review it.

## Existing capabilities to reuse

- `src/Forge.Host/wwwroot/js/app.js` already filters navigation by effective permissions and exposes Home/Plant Overview, Workforce Kanban, Training & Performance, Planning, Shop Floor, Quality, Materials, Maintenance, and My Work as distinct workspaces. Home and Plant Overview currently use the Horizon page.
- `src/Forge.Host/wwwroot/js/pages/workforce-intelligence.js` and `performance.js` already present source-backed workforce coverage, qualifications, attendance, training, performance context, and supervisor recommendations. The Command Center labels recommendations as requiring review.
- `src/Forge.Kernel/WorkAssignments/WorkAssignments.cs` provides audited, permission-checked assigned work with source revalidation. Its lifecycle is `Assigned → Acknowledged → InProgress → Completed`; it must not be used to claim a production order, shipment, quality release, or inventory transaction is complete. A mission may link to this queue where appropriate, while authoritative completion remains in the existing source workflow.
- Forge already has site time-zone support, worker shift fields, role/permission and program-scoped access checks, audited command pipelines, notification delivery, and evidence-bearing workflows for orders, inventory, quality, maintenance, and workforce. These are integration points, not justification for copying their business state into mission rows.

## New work the specification requires

- A server-side, read-only mission projection that gathers only data authorized for the current identity and scope, records source freshness/version, and links each item to its authoritative source.
- Operational-day semantics based on the site time zone **and** assigned shift/calendar, including overnight shifts. Site-local dates and worker shift fields alone do not provide the required once-per-operational-day identity or cross-device briefing state.
- Persistent Daily Plan and first-login briefing state, including dismissal separate from approval, role/scope changes, stale/partial-data notices, and a multi-role workspace selector/preferences.
- Mission-specific accept/modify/defer/reject and conflict handling, if enabled, with expected-version checks, idempotency, audit reasons, permission checks, and revalidation through each existing command. The example `mission_item` status must never become the source of operational completion.
- Role-specific workspace composition, program-scope-safe aggregation, explainable deterministic prioritization, notification/update policy, accessibility coverage, and the WhiskerWorks acceptance matrix.
- Hawk artwork/preferences are optional visual polish and should follow the operational workflows.

## UI review and implementation guidance

The experience principles are strong: action-first, explainable, dismissible, permission-aware, and safety/quality constrained. The document is an interaction/spec brief rather than a visual mockup; it does not define a finished screen composition or a specific role-priority algorithm. The proposed first-login briefing plus persistent Daily Plan is a good shell, provided each card includes its source record, reason, freshness, blocker, and only the next action the user is authorized to take.

The suggested `mission_item`/`mission_decision` entities need to remain a projection and decision log, not a shadow workflow. In particular, do not duplicate work-assignment status, invent a completion checkbox, persist copied inventory or attendance facts, or expose restricted program names/counts in a summary. Use source references and current source reads; mark a projection stale when it cannot safely refresh. Keep the current Classic Workspace available during rollout.

The scope spans an aggregator, time semantics, persistence, eight role workspaces, controlled commands, accessibility, and at least 20 explicit scenarios. It should be delivered in the document’s phases. Start Phase 1 read-only, prove authorization/freshness and operational-day rules, then add the briefing and persistent UI. Enable consequential actions only after each action maps to an existing transaction and passes hard-gate/concurrency tests. Do not build a parallel scheduler or recommendation calculator.

## Phase 2 implementation update — 2026-10-25

The first-login briefing and workspace preference foundation is now implemented. Migration `0036_daily_mission_workspace_state.sql` stores only presentation state. Briefing rows are unique by person and operational date, so an overnight shift reuses the date on which that shift began and multiple devices do not repeatedly show the first panel. Viewing and dismissal are separate from every source workflow. Site/shift or authorization-scope changes update the current context and show a nonintrusive notice instead of forcing another first-session panel during that operational date.

The client checks the authenticated operational-day session at sign-in, opens Daily Mission for a first briefing, and otherwise follows the user's saved role/scope-aware landing preference. It resolves shift context first and only computes the full source projection when a new briefing is claimed. An authorized top-bar workspace selector works across pages; the classic sidebar remains available, and Classic Workspace is offered when permission allows it. Hawk accents can be set to off, subtle, or expressive. Open Daily Plan, Review Recommendations, Dismiss for Now, and View Shift Briefing are keyboard-accessible, respect reduced-motion settings, and do not approve or change operational records.

Workspace preferences now include a saved program view of All authorized programs or a single program already in the principal's grant set. The mission endpoint narrows a copy of that set before program-aware sources run; choosing a program cannot grant access. Shared site-scoped sources remain under their own read permissions. Labels use program names only when `ProgramsRead` is authorized.

The read-only mission also lists pending receipt inspections at current-site locations and current equipment failures/indeterminate results for authorized open production operations. Both source families are marked limited and linked back to the existing Receiving or Production Order workflows. Material-constrained order cards now expose their existing allocation quantities and scheduled supply dates; when Inventory and Resources reads are allowed, they also show current-site stock disposition for affected parts. Site totals are explicitly not reservations and do not replace the material allocation engine. Full inventory availability, a general supplier ETA view, and the full machine readiness board remain incomplete. Partial domains now report `Limited` and describe missing coverage instead of appearing wholly disconnected.

Attendance now includes aggregate verified ApprovedPto counts for the current or upcoming assigned shift. It omits names/reasons and does not count protected leave, disputed/pending/superseded/conflicting classifications, or infer a future call-out/no-show.

Assigned Work cards can advance only the existing assignee-owned Work Assignment lifecycle (`Assigned` → `Acknowledged` → `InProgress` → `Completed`) through its audited command with a required reason. The UI makes clear that even `Completed` means only the assignment record is complete; the linked business workflow remains authoritative. No generic mission defer/reject/approve action was created.

Mission snapshots older than five minutes (or with an invalid generation timestamp) display a stale warning and disable assignment progression until refresh. The source command still performs current-state and source-access checks when submitted.

Role/workspace policy tests and UI interaction tests cover permission-filtered options, role defaults, scope changes, dismissal/reopening, preference writes, program-scope narrowing, audited assignment transitions, and stale-action blocking. The host and integration-test project build with 0 warnings/errors; workspace policy tests pass 3/3, focused Daily Mission UI tests pass 3/3, and the complete UI suite passes 390/390 across 57 files. The ApprovedPto calculator tests must be rerun after this last attendance change. PostgreSQL migration/state execution is still unverified because `FORGE_TEST_POSTGRES` is unset and the Docker engine is unavailable. Remaining source gaps are full qualification-aware workforce coverage/reassignment, full inventory availability and general supplier ETA monitoring, and comprehensive machine readiness. Mission-specific actions beyond existing source workflows remain unimplemented; any additional action must use its authoritative transaction and hard gates.

## Phase 2 continuation — safe coverage and readiness-passed operations — 2026-10-25

Workforce-primary order cards offer authorized supervisors an on-demand read-only recovery preview. The new endpoint revalidates that the exact released operation is still workforce-blocked, confirms the authenticated worker's current/upcoming shift and site, applies the saved program narrowing, and checks supervisor/manager permission scoped to the target work center. It then reuses Forge's existing recovery and skill-capacity services, so qualification, safety, skill recency, capacity range and originating-station effects come from authoritative calculations. No candidate names are placed on general mission cards; no workforce assignments are committed by the preview.

The new **Ready to Execute** section lists up to five open released operations at the user's site whose current order-readiness checks pass. The card explains that it does not reserve schedule capacity, confirm an approved dispatch, or begin work. The source remains `Limited` to reflect that boundary.

Workforce-blocked, equipment-blocked and readiness-passed operation cards, along with the maintenance readiness source, are scoped to work centers/machines mapped to the authenticated worker's site. Machine-linked maintenance assets are included even when their resource records are retired. These sources are withheld as `Limited` when site context or the resource map cannot be read; they do not emit unfiltered plant-wide cards.

Verification now passes the ApprovedPto calculator tests **7/7**, workspace policy tests **3/3**, site-scope tests **2/2**, the full UI suite **391/391**, JavaScript syntax checking, and `git diff --check`; the latest Release test build rebuilt the Host and Integration.Tests successfully. PostgreSQL-backed migration/state and source endpoint integration have not been verified because `FORGE_TEST_POSTGRES` is unset and Docker is unavailable. General current-site inventory availability and supplier ETA monitoring, a complete equipment-readiness projection within Daily Mission, and the full WhiskerWorks scenario acceptance matrix remain open. Consequential mission decisions beyond the existing source workflows remain intentionally out of scope until their source-command and concurrency gates are proven.
