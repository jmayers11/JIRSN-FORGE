## Delivered increment 1: Manufacturing Flow Map

`src/Forge.Host/wwwroot/js/pages/orders.js` adds a **Flow** tab to the existing Production Order workspace. It uses the same order routing and readiness response as the detailed Operations table; there is no new readiness or scheduling engine and no production mutation. The view:

- Shows the released route as ordered operation cards, with work center, best identified machine, planned time, good/scrap quantities, execution state and currently recorded crew.
- Opens the first current evaluated blocker by default and shows its evidence, affected later incomplete operations on that track, and a link to the existing source workflow.
- Separates complete, running, ready, waiting, blocked and unknown states. Missing readiness reads and unevaluated dimensions are never rendered as ready.
- Keeps approved rework operations in separate tracks. It explicitly states that source data has no cross-track origin link; it does not invent a branch or loop edge.
- Includes the readiness snapshot time and a refresh action. The original detailed Operations table remains available as a sortable accessible fallback. The existing Readiness panel is also kept, with its unknown states called out explicitly.

This increment is intentionally read-only and embedded in the work-order context at `#/orders/{orderNumber}`. It is controlled by the default-on `Forge:Features:OperationalVisualizations` configuration flag; set it to `false` to hide the new Flow tab while leaving existing order and readiness behavior unchanged. It adds no separate dashboard, PPA, new data pipeline, migration, or production mutation.

## Delivered increment 2: contextual readiness and Inventory Location Map

Production Order **Readiness now** includes the existing partial-build preview action for released orders where the user can read the approved schedule. The action reuses `/api/planning/orders/{order}/partial-build-preview`; it does not write. Its UI calls out that its feasible quantity is bounded by the preview's material and approved WIP logic and is not the maximum across quality, workforce, equipment, tooling and documentation gates. The operation readiness table and Flow continue to show each engine dimension separately and never average them.

Inventory **Location map** is at `#/inventory?tab=map` and extends the existing Inventory page. It is loaded only while selected and uses the existing locations, positions and storage rules reads. The map cards are ordered and indented from configured parent paths; they do not claim physical coordinates. Each stock row retains quality status, custody, nettable/usable status and whether it is available for planning. The WIP rule's server-computed limit, on-hand quantity, reservations and free amount are shown; mixed-part or unavailable evidence remains `Unknown`. Work-order search uses the permission-checked inventory ledger endpoint and labels transactions as historical movement evidence. The position model provides no item age or direct current work-order link, so neither is fabricated. The accessible table alternative remains available.

The views are controlled by the default-on `Forge:Features:OperationalVisualizations` flag. The UI uses existing permission-checked APIs; map reads are deferred until requested, and the WO transaction endpoint keeps its program-scope filtering. No database migration, new endpoint, polling, recommendation engine, or production-state mutation was introduced.

## Delivered increment 3: operation-centered Workforce Coverage Matrix

Training & Performance (`#/performance`) now includes an **Operation coverage matrix** in its existing Coverage tab. The matrix reuses the page's existing workers, qualifications, machine authorizations and unavailability reads. Its operation columns are built from configured machine/activity profiles; employee rows honor authorized site, selected shift, department, role and active-status filters while allowing cross-work-center visibility within the selected site. Each operation expands to an accessible evidence table. Qualification is explicitly not placement approval; current presence, safety composition, source work and capacity need a separate preview.

Supervisors with readiness-read and workforce-supervision permissions can request the existing `/api/readiness/workforce-recovery-capacity` preview for a selected operation. It fetches only when requested, displays feasible candidates, the engine's origin-work impacts, expected setup/output range and confidence where returned, and states that nothing is assigned. Backend readiness, authorization, safety and schedule rules remain authoritative. The matrix and preview add no endpoint, migration, recurring polling or mutation. The matrix shows the time the page's source reads completed; source APIs do not provide one shared snapshot token or per-source server timestamps, so this is not represented as a transactionally consistent server timestamp.

## Delivered increment 4: same-snapshot recovery comparison

The existing Scenarios page could evaluate one recovery option at a time but replaced the prior selection. It now retains distinct choices as the user evaluates alternatives and submits them together in `ScenarioChange.RecoverySelections`. Forge's existing Planning Scenario service runs each choice independently against the same copied source snapshot; no choice is applied as a source command. The comparison panel at `#/scenarios` puts current baseline, disruption case and each selected trial side by side by affected work order, including feasibility and projected completion/status. It explicitly notes when fewer than two selected options currently pass the evaluated gates and discloses which production dimensions the current response does not provide.

This is a partial recovery simulator: it does not claim per-operation good output, setup/labor loss, material/WIP deltas, cost or complete plant-wide consequences for every option. Source-action authority remains a separate read-only gate and actual changes still open their owning workflows. The comparison and matrix are included in the default-on `Forge:Features:OperationalVisualizations` flag. No solver, API endpoint, database migration, background poller or production mutation was added.

## Delivered increment 5: cross-source order connections in Daily Mission

Daily Mission already gathers permission-scoped planning, material, quality, machine, workforce and other source items. Cards now expose a collapsed **Related signals** list when two or more items have the same exact canonical `#/orders/{orderNumber}` source link. Each link jumps to the related card, where its own source workflow can be opened. The list keeps source lifecycle, status and timestamp visible and explicitly says that a shared order reference is not a combined risk score or proof of a shared physical cause. It does not parse free text, widen permissions, call more APIs, or mutate operations. The connection is controlled by `Forge:Features:OperationalVisualizations`.

## Remaining delivery work

Remaining: (1) close the simulator gaps in operation-level output, setup/labor, material/WIP and whole-plant impact only if the existing solver can return those measures; (2) implement a Risk Radar only after future-horizon inputs, rule thresholds, deduplicated causes and freshness semantics are validated; and (3) extend the existing Plant Floor only where a verified data source adds value, including any useful multi-floor/revision support. The seven-view request is therefore partially implemented, not complete. The current plant map remains the existing Workforce Kanban view; it must not imply connected telemetry. Missing evidence must stay explicitly unknown.
